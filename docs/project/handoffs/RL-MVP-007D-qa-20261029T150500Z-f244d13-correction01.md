## Correction 1 — crash-safe owned Ollama lifecycle

### What is fixed

Exact source now:
- starts a dedicated supervisor in a new session;
- keeps a parent-owned lifetime write pipe;
- passes only the supervisor read end/status FD/verified executable FD;
- does not pass the lifetime write end to the Ollama child;
- supervisor observes EOF when the parent dies;
- supervisor terminates, then kills/reaps a non-cooperative child;
- unknown pre-existing listener remains rejected;
- normal close closes the parent lifetime writer and waits for supervisor cleanup.

This resolves the original orphaned-child design defect in the ordinary abrupt-parent-death path.

The new tests explicitly cover:
- abrupt application exit with a harmless subprocess;
- child start failure;
- supervisor Popen failure;
- handshake exception;
- SIGTERM-resistant child fallback.

### Remaining defect A — MEDIUM: already-exited supervisor can leak the lifetime FD

Exact source:

`_terminate_process(process)` immediately returns when `process.poll() is not None`.

For `_SupervisedProcess`, closing its private `_lifetime_fd` happens only inside `terminate()`.

Therefore, if the supervisor exits on its own before parent cleanup — for example child startup failure or unexpected child exit — `_terminate_process()` can return without ever closing the parent's lifetime writer.

**Independent code-only reproduction actually run**

A standalone clone of the exact `_terminate_process` / `_SupervisedProcess` ordering used an OS pipe and an already-exited fake supervisor.

Observed:

`already_exited_supervisor_lifetime_fd_still_open = True`

No Ollama, model or network was involved.

**Impact**

This is not an Ollama orphan once the supervisor is already dead, but repeated runtime startup/child failures can leak FDs in the long-lived API process and eventually exhaust resources. It also contradicts the correction's claimed exact pipe-FD cleanup.

**Minimal correction**

Ensure supervised lifetime ownership is closed regardless of supervisor poll state. For example:
- close `_SupervisedProcess` lifetime FD before the early-return check; or
- provide an explicit idempotent `close_lifetime()` and invoke it in every cleanup path; or
- make `_terminate_process` special-case `_SupervisedProcess` so `terminate()` is always called at least once.

Add a regression with `poll() == 0` before cleanup and assert the lifetime FD is closed, plus a real harmless startup-failure race repeated enough times to prove no descriptor growth.

## Correction 1 / macOS executable identity limitation

### Acceptable residual: same-user path replace-and-restore race

The supervisor retains the verified executable FD and compares the audited absolute pathname's device/inode/metadata against that FD immediately before and after spawning the child.

Because macOS lacks the Linux-style atomic FD execution path used by the prior design, a malicious process running as the **same local user** could theoretically:
1. replace the pathname between checks;
2. cause exec of the substitute;
3. restore the original inode/path before the post-spawn check.

That is a real race. The current application already treats a hostile same-user host/account compromise as outside the narrow local trust boundary. Parent directories must be root/current-user owned and not group/other writable. Within that stated threat model, I consider this residual race acceptable **if explicitly documented**. It would require a native FD-exec/helper or stronger OS sandbox to eliminate, which is outside E0068.

### Remaining defect B — IMPORTANT / blocking: version attestation still uses /dev/fd on macOS

The corrected supervisor switched actual `serve` startup to the audited pathname, but `InferenceRuntime.verified()` still performs:

`subprocess.run([f"/dev/fd/{executable_fd}", "--version"], ...)`

The Backend handoff itself records that on macOS:
- there is no `fexecve` / `execveat`;
- direct Mach-O execution through `/dev/fd/<fd>` returns permission denied.

The exact test suite mocks `subprocess.run` and explicitly expects `/dev/fd/<fd>`; it therefore does not exercise the real supported-platform behavior.

**Impact**

On the sole supported target (macOS arm64), a correctly pinned legitimate Ollama binary can fail at version verification before supervisor launch. The code-only runtime remains fail-closed, but the qualified real-inference path is not operationally viable.

**Independent status**

I did not execute a Mach-O binary because this review environment is not the authorized macOS runtime target. The defect is supported by:
- exact-source inspection showing `/dev/fd` remains in the real version command; and
- the Backend's own documented macOS platform observation.

**Minimal correction**

Use the same audited pathname strategy for `--version` that is used for `serve`, while retaining the opened descriptor as the identity anchor:
1. verify pathname identity equals retained FD immediately before the version subprocess;
2. run `[str(executable), "--version"]`;
3. immediately re-check pathname identity;
4. re-hash/revalidate the retained FD;
5. fail closed on any mismatch.

This leaves only the documented same-user replace-and-restore race already accepted by the local threat model.

If atomic FD execution is required instead, stop for a native-helper/sandbox scope amendment.
