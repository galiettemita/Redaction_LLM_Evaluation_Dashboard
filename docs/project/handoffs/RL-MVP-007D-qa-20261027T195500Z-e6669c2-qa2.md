### Finding 1 — HIGH — abrupt application death can orphan the owned Ollama process and permanently block restart

**Observed exact source path**

`InferenceRuntime._start_owned_runtime()` uses an ordinary `subprocess.Popen(...)`. The child process has no parent-death watchdog, inherited lifetime pipe, supervisor, or recoverable ownership record.

Normal error paths call `VerifiedInferenceRuntime.close()`, which terminates/kills the child. But abrupt parent death (SIGKILL, interpreter crash, host process termination outside Python finally handling) skips that cleanup.

On the next process start, `_start_owned_runtime()` deliberately probes `127.0.0.1:11434` and rejects **any** pre-existing listener as:

`refusing an unowned pre-existing model runtime`.

Therefore an Ollama child orphaned by a prior Redaction Lab process can remain bound to the port and make every subsequent explicit process/resume attempt fail until an operator manually identifies and kills it.

This conflicts with the E0065 crash/restart recovery objective and makes the application unable to distinguish a hostile listener from its own orphan.

**Independent reproduction actually executed**

Code-only subprocess lifecycle probe, no Ollama/model/PDF:

1. parent Python process starts a child process with ordinary `subprocess.Popen`;
2. parent writes child PID and exits via `os._exit(0)`;
3. reviewer checks the child after parent death.

Observed:

`child_survives_parent_exit=true`

The surviving child was then killed by the QA probe.

This directly reproduces the lifecycle primitive used by the candidate; no prohibited runtime was executed.

**Minimal correction**

Add a parent-death ownership mechanism before real runtime qualification. Preferred narrow design:
- start the pinned Ollama executable under a tiny application-owned supervisor/watchdog process;
- parent keeps a dedicated pipe/FD open;
- supervisor terminates/kills the Ollama child when it observes EOF from parent death;
- retain the existing pinned executable FD, model-store identity, loopback and API checks;
- add an abrupt-parent-exit regression proving the listener disappears without manual cleanup.

Alternative recovery is acceptable only if restart can cryptographically/structurally prove a surviving listener is the exact previously-owned process before terminating/reusing it. Do **not** weaken the current “reject unknown listener” rule.

### Finding 2 — HIGH / IMPORTANT — a consistently substituted model lock is not bound to the approved service model before durable run-intent mutation

**Observed exact source path**

`InferenceRuntime.verified()` verifies:
- lock `model_id == provider_model_id`;
- executable/version/hash;
- model-store complete inventory and hashes;
- API-reported model name/digest equals the lock.

It does **not** require the verified runtime model identity to equal the E0065 approved service model constant:

`qwen2.5:1.5b-instruct-q4_K_M`.

`PredictionService._run_definition()` independently hardcodes that qwen model into the Task-4 run.

`PredictionService.run()` then:
1. obtains a “verified” runtime;
2. creates/fixes the qwen RunDefinition;
3. persists missing target intents;
4. only during `run_job_once()` does `adapter.request_hash()` call `OllamaAdapter.prepare()`, which rejects the qwen manifest if the adapter itself is bound to a substituted model.

Because request-hash preparation occurs before `store.claim()`, no attempt is claimed, but **the run and PENDING target intents have already been durably frozen**.

A later corrected runtime with a different model config/manifest identity cannot simply resume that frozen service run; the stored v0.2 runtime identity no longer matches the corrected runtime, leaving a durable unusable run that must be specially handled.

**Independent adversarial reproduction actually executed**

Code-only ordering reproduction using the exact candidate semantics:
- runtime lock model = `substituted-model`;
- provider model = same `substituted-model`, so runtime’s internal equality check passes;
- service run model remains hardcoded qwen;
- two target intents are persisted;
- adapter request preparation rejects qwen vs substituted model before claim.

Observed:

- `dispatch_error=manifest model does not match adapter model`
- `persisted_intents=2`
- `attempt_claimed=false`
- `later_corrected_runtime_blocked=true`

No network/model/runtime operation occurred.

**Test gap**

Candidate inference-runtime test mutates only `model_id` while leaving `provider_model_id` unchanged; that exercises the lock-internal mismatch check, not the attack where **both are consistently substituted**.

**Minimal correction**

Before constructing or persisting any run/intent, bind the verified runtime model to the approved service model:

```
verified = InferenceRuntime().verified()
if verified.adapter.model_id != MODEL_ID:
    verified.close()
    raise InferenceRuntimeUnavailable(...)
```

Perform that check **before** `_run_definition()` / `RunStore.enqueue()`.

Add an exact regression where both lock `model_id` and `provider_model_id` are the same unauthorized substitute, all hashes/version/API identity otherwise match, and assert:
1. service fails before mutation;
2. zero new Task-4 jobs/intents exist;
3. a later corrected approved runtime can create the intended run.

Prefer also making the frozen runtime identity explicitly include the approved model ID rather than inferring it from a separate RunDefinition constant.

### Finding 3 — MEDIUM — a real oversized Ollama HTTP response is classified ERROR instead of MALFORMED

**Observed exact source path**

`OllamaAdapter._stdlib_transport()` reads `MAX_RESPONSE_BYTES + 1` and raises:

`ValueError("response exceeds size limit")`

when the response is oversized.

`OllamaAdapter.predict()` catches `ValueError` in the transport exception block and maps non-timeout transport exceptions to:

`AttemptStatus.ERROR`.

The later `MALFORMED` branch for `len(raw) > MAX_RESPONSE_BYTES` is therefore unreachable for the normal stdlib transport, because the real transport already raised.

The existing test `test_private_transport_mock_cannot_bypass_response_size_limit` monkeypatches the transport to *return* oversized bytes, which exercises the later MALFORMED branch but not the actual production transport behavior.

This violates the requested distinction between provider/runtime ERROR and malformed/oversized provider content.

**Independent reproduction actually executed**

QA started a local synthetic HTTP server on ephemeral `127.0.0.1` that returned a response larger than 1 MiB and reproduced the candidate’s exact read/catch logic. No Ollama/model/provider was involved.

Observed candidate classification:

`candidate_status=ERROR`

The underlying read ended as a local connection/reset/oversize transport exception, which the candidate maps to ERROR.

**Minimal correction**

Either:
- return the bounded+1 raw bytes from `_stdlib_transport()` and let `predict()` classify `len(raw) > MAX_RESPONSE_BYTES` as MALFORMED; or
- raise a dedicated `OversizedResponse` exception and map that exception explicitly to MALFORMED.

Add a test using the actual stdlib transport against a local synthetic HTTP server with an oversized response; do not monkeypatch `_stdlib_transport` itself.

### Finding 4 — MEDIUM provenance/maintainability — run_id is not a complete semantic fingerprint of RunDefinition

**Observed exact source**

The v0.2 `run_id` hash includes:
- source ID;
- canonical hash;
- ordered target versions;
- model ID;
- prompt ID/version;
- settings;
- model config ID;
- model manifest digest.

It omits semantically relevant frozen run fields such as:
- `RUN_VERSION`;
- experiment condition;
- `COMMON_CONTEXT_BUDGET`;
- context policy;
- tool permissions;
- budget label/service identity.

The store also persists and validates full `run_json`, so a mismatch on an existing database fails closed; this is not a leakage/duplicate-dispatch bypass. But two semantically different run definitions can calculate the same nominal `run_id`, which weakens provenance identity and creates avoidable collision/fail-closed migration behavior across code revisions.

**Independent reproduction actually executed**

QA reproduced the exact `_identity` formula. Changing each omitted semantic field while keeping the currently hashed values constant produced the exact same run ID:

- `run_version_same_id=true`
- `experiment_condition_same_id=true`
- `common_context_budget_same_id=true`
- `context_policy_same_id=true`
- `tool_permissions_same_id=true`
- `budget_label_same_id=true`

**Minimal correction**

Include all prediction-affecting/frozen semantic fields in the run identity payload, or hash a canonical complete run-intent structure whose contents are also used to construct `RunDefinition`.

Add a regression proving every semantic run field that can change behavior changes `run_id`.
