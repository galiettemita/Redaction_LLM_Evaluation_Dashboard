## QA / security findings

### HTTP request bounds — PASS

Upload POSTs require a strict decimal Content-Length and cap the request body at:

`MAX_PAIR_BYTES + 64 KiB multipart overhead`.

The multipart parser separately enforces:

- 25 MiB per PDF;
- 50 MiB combined PDF bytes;
- required redacted PDF;
- `%PDF-` signature;
- nonblank bounded UTF-8 project ID;
- exactly the three contract fields only.

Base64 and other expanding Content-Transfer-Encoding modes are rejected, preventing decoded-body expansion after the outer byte bound.

### Multipart framing / ambiguous Content-Type — PASS

The top-level Content-Type is constrained by an anchored ASCII regex to exactly one `multipart/form-data; boundary=...` parameter.

The parser rejects:

- duplicate boundary parameters;
- appended media types;
- extra top-level parameters;
- CR/LF header injection;
- malformed/missing closing boundary;
- nonempty preamble/epilogue;
- nested multipart parts;
- duplicated Content-Disposition, Content-Type or Content-Transfer-Encoding headers;
- duplicate resolved form fields;
- unrecognized fields;
- non-PDF file Content-Type.

I found no demonstrated request-smuggling or role-confusion path in the single local WSGI parsing boundary.

### Host / Origin / loopback checks — PASS for API layer

Every route, including health, is gated before dispatch.

The API requires:

- `REMOTE_ADDR == 127.0.0.1`;
- literal Host `127.0.0.1[:port]`;
- HTTP/HTTPS only;
- if Origin is present, exact scheme/host/port equality with no userinfo, query or fragment.

This blocks DNS-rebinding Host values and cross-origin browser POSTs at the application layer.

Actual socket binding is not performed by 7B; 7P owns the server/launcher. Therefore this PASS does **not** claim a listening service is genuinely bound only to 127.0.0.1 until 7P is reviewed.

### Failure handling / path safety — PASS

Unknown IDs return redacted 404s.

Artifact integrity failures and unhandled internal failures return generic path-free 500 responses. SQL lookups are parameterized and route IDs are never used as filesystem paths.

The API exposes no deletion or general artifact download route.

### Concurrency and application state transitions — PASS

Within one API process, upload/process orchestration is serialized with a lock.

Across processes, the integrated ApplicationStore remains the durable authority:

- SQLite transaction/partial unique index preserves one PROCESSING document job;
- `DocumentWorker.claim_next` remains the claim authority;

The process endpoint checks that the requested job is still ACCEPTED and is the earliest accepted work before invoking DocumentWorker, so the route does not accidentally claim a different queued job.
