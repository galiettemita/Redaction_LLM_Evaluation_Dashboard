## Original QA blockers — status

### Authentic frozen Task-4 attempt authority — RESOLVED

`RunStore.resolve_attempt` now resolves from immutable Task-4 SQLite state and revalidates trusted source, frozen run, manifest, attempt identity, request hash, model configuration, provider-model provenance and expected terminal/IN_DOUBT state. It is read-only and introduces no dispatch/retry path.

A caller-created `ModelAttempt` alone is no longer sufficient for the authoritative `EvaluationStore.evaluate_and_store` path.

### Forged direct EvaluationRecord authority — RESOLVED in the authoritative store path

`EvaluationStore` does not expose `save_evaluation(record)`. Authoritative evaluations are created from a resolver-authenticated Task-4 attempt plus re-derived DEC-022 mapping authority. Stored rows are immutable, project-scoped on read, deterministically identified and rechecked against Task-4 bindings.

Directly constructed `EvaluationRecord` values remain possible as value objects for backwards compatibility, but they are not accepted into the authoritative repository path.

### Forged direct SummarySnapshot authority — RESOLVED in the authoritative store path

`EvaluationStore` does not expose `save_summary(snapshot)`. Authoritative summaries are built from exact requested attempt IDs and stored evaluation IDs, persisted together with member rows in one transaction, reloaded by project, and recomputed from underlying attempts/evaluations before return.

Direct `SummarySnapshot` construction remains possible as a value object; callers must not treat such objects as repository authority. This is a nonblocking API-trust caveat, not an observed authoritative-storage bypass.

### Cross-document/model-specific run semantics — RESOLVED for successful/like-shaped evaluations

The v2 authoritative summary path supports multiple contributing run IDs at MODEL level and retains run-local requirements at TARGET/DOCUMENT levels. The exact candidate includes real-shaped tests for:

Protocol compatibility now binds condition, prompt/version, settings fingerprint, attempt policy, context policy/budget, tools, rubric/evaluator/judge, mapping method and model/config provenance.

### Unvalidated fact segmentation / mock judgment — RESOLVED

## BLOCKING finding 1 — common eligible set is model-outcome dependent because it includes source-fact-record identity

Severity: **High / cross-model comparability defect**.

The correction requires cross-model comparisons to use the exact same **eligible target/reference set**, while keeping technical nonanswers orthogonal to truth eligibility.

The exact v2 implementation computes each eligible provenance key from:

- project/document/target identity;
- mapping/reference versions/hashes/method;
- DEC-022 trust;
- **source_fact_record_id**;
- **source_fact_record_version**.

However `evaluate_attempt` only assigns `source_fact_record_id/source_fact_record_version` inside the successful semantic-evidence branch. A technical nonanswer such as TIMEOUT, REFUSED, ERROR or MALFORMED can still have trusted, fully eligible DEC-022 truth, but its evaluation carries null source-fact-record identity.

Therefore two model summaries over the same target and same exact approved reference can receive different `eligible_provenance_keys` solely because one model produced an answer and the other produced a technical nonanswer.

Independent exact-logic reproduction:
- successful evaluation key with `source-facts-1/source-facts-v1`;
- TIMEOUT evaluation key with `None/None`;
- all project/target/mapping/reference trust inputs identical;
- keys are different.

`assert_comparable_summaries` requires identical `eligible_provenance_keys`, so this pair is rejected as an eligible-reference-set mismatch.

That makes the common eligible set dependent on the model's outcome/evaluation path, contrary to the requirement that:
- truth eligibility be model-independent;
- technical nonanswers remain separately counted rather than alter the comparable truth set.

### Required correction

Define the cross-model common eligible identity only from target/reference truth provenance required by the Correction-01 packet: project, redacted document/target versions, mapping/reference versions/hashes/method and DEC-022 trust. Keep source-fact/rubric/judge compatibility as separate summary/protocol compatibility evidence, not as part of the target/reference eligible-set identity.

Add a regression where:
- model A succeeds on a trusted target with a source-fact record;
- model B TIMEOUTs or REFUSEs on the same trusted target and therefore has no source-fact record;
- both MODEL summaries retain the same common eligible target/reference set and are comparable while technical outcome counts differ.

This is blocking because it directly affects fair model comparison and the requested handling of technical nonanswers.

## BLOCKING finding 2 — exclusion-only authoritative summaries cannot be represented

Severity: **Medium-High / requested-membership and exclusion reporting defect**.

Correction 01 requires:
- requested attempt IDs;
- exact included evaluation IDs;
- explicit exclusions;
- every requested attempt assigned to included or excluded membership;
- empty eligible denominator => null, never zero.

`EvaluationStore.build_summary` supports explicit `NO_EVALUATION` exclusions, but `build_authoritative_summary` immediately calls `_authoritative_profile(ordered, ...)`. That function raises if there are no included evaluations:

`at least one included evaluation is required`.

Therefore a valid request in which every requested attempt is explicitly excluded for `NO_EVALUATION` cannot produce the requested authoritative summary/count record at all.

This matters for durable reporting of an entirely unevaluated requested set: the system cannot persist `requested_count=N, excluded_count=N, eligible_count=0` with null score channels even though the correction explicitly models exclusions and exact requested membership.

### Required correction

Either:
- support exclusion-only summaries by deriving the protocol/model/scope profile from the already resolver-authenticated requested attempts and recording the absence of evaluator/rubric evidence explicitly; or
- narrow the approved summary contract with an explicit invariant that at least one authoritative evaluation is required and explain where all-excluded requested sets are durably represented.

The current packet requires the former behavior more naturally; no such narrowing is recorded.
