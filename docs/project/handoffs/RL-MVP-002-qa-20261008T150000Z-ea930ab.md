## Four prior blocking issues — fresh assessment

### 1. Project-scoped deterministic identity — RESOLVED

The v3 identity formula remains JSON-encoded and includes project ID, document-version ID, page, normalized geometry and detector version. Independent probes again confirmed:
- different projects with the same local document/version/geometry produce distinct IDs;
- delimiter-bearing identity components cannot collapse into the same serialized identity.

No regression observed.

### 2. Sparse / multi-column reading-order ambiguity — STILL BLOCKING

Correction 02 improves sparse-column handling. It now catches:
- two separated spans on the same line;
- a one-line secondary span separated from a repeated main-column start;
- the earlier wide/narrow/staggered multi-line column patterns.

However, it still misses **two staggered one-line columns when neither column start repeats and the two spans are on different baselines**. In that case:
- each line has only one spatial span, so `split_line` is false;
- neither start repeats twice, so `repeated_starts` is empty;
- `sparse_secondary_column` is false.

Independent execution of the exact helper returned:
`staggered_two_one_line_columns False`.

A minimal example is one line at x≈72/y≈720 and one line at x≈330/y≈680, with a normal supported black overlay over text in one column. This remains an ambiguous positioned two-column layout, but the detector can treat it as supported and allow canonicalization. The Correction 02 packet explicitly requires sparse/two one-line columns to fail closed rather than risk reordered context.

**Required correction:** add a conservative rule for separated sparse spans on different baselines when the page cannot prove a single reading flow, plus a regression for staggered two one-line columns and negative controls that avoid rejecting legitimate single-column paragraphs/indents.

### 3. Overlapping / duplicate rectangles — RESOLVED

The prior text-related overlap guard remains intact. Independent predicate checks confirmed overlapping/duplicate geometry is intersecting while adjacent separated boxes are not. No Correction 02 change regressed the routed overlap fix.

### 4. Standalone no-glyph boundary redaction — IMPROVED BUT STILL BLOCKING

Correction 02 replaces proximity-limited `_near_text_block` with `_aligned_with_text_block`, so a no-glyph black rectangle at the beginning/end of a section is now treated as ambiguous even when the only visible context is far above or below, **provided the rectangle horizontally overlaps at least one visible character**.

That closes the exact x-aligned start/end regressions added by Backend, but it still silently ignores plausible one-sided boundary redactions that are positioned within the document's text region without literal horizontal overlap with the only visible line. Example:
- visible text starts at x≈72 and ends around x≈250;
- a standalone black text-sized rectangle at x≈260–380 appears above that line at a section/document boundary;
- no underlying extractable glyphs are present.

For this case:
- `_same_text_flow` is false because there is no vertical overlap;
- `_aligned_with_text_block` is false because there is no x-overlap;
- the detector follows `ignored_artwork_count += 1` and can return false `NO_REDACTIONS`.

Independent probe output:
- aligned start-boundary rectangle -> `aligned=True`
- right-shifted plausible start-boundary rectangle -> `aligned=False`
- clearly remote artwork -> `aligned=False`

The Correction 02 requirement is stronger than exact x-alignment: plausible first/last-line redaction-shaped boxes must not be ignored without affirmative artwork evidence. A nearby/right-shifted text-sized box in the page's text region remains ambiguous, not proven artwork.

**Required correction:** define a conservative page/text-region evidence rule for one-sided standalone boxes rather than requiring literal horizontal intersection with existing text. Keep a strong remote-artwork negative control so distant decorative blocks remain `NO_REDACTIONS`.
