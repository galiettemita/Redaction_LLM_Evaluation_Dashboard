# Findings

## Finding 1 — IMPORTANT — macOS target runtime still executes the version probe through /dev/fd and can never reach qualified launch

### Exact source

`InferenceRuntime.verified()` still runs:

```python
subprocess.run(
    [f"/dev/fd/{executable_fd}", "--version"],
    ...
    pass_fds=(executable_fd,),
)
```

The corrected supervisor intentionally switched actual runtime launch to the audited absolute path:

```python
subprocess.Popen([str(executable), "serve"], ...)
```

because E0068's Backend handoff reports the macOS limitation:

- macOS has neither usable `fexecve` nor `execveat` for this purpose;
- direct Mach-O execution via `/dev/fd/<fd>` returns permission denied.

The target package is explicitly Darwin/arm64. Therefore the retained `/dev/fd` **version check occurs before the supervisor launch** and blocks the intended target runtime even if the executable, lock, model files and API identity are otherwise valid.

### Independent evidence

This QA environment is Linux and E0068 prohibits running a real Ollama binary, so the macOS Mach-O execution itself was **NOT independently executed**.

However:
- exact corrected source still contains the `/dev/fd/<fd> --version` invocation;
- exact Backend correction evidence explicitly reports that this invocation fails on macOS;
- the code has no Darwin-specific alternative around the version probe.

This is a source/evidence contradiction affecting the sole supported platform, not a speculative hardening request.

Public platform references also support that macOS lacks an officially supported arbitrary-FD `fexecve` equivalent and `execve("/dev/fd/<n>")` can fail with EACCES. That external corroboration was used only to assess the portability limitation; the repository source and Backend observation are sufficient to identify the blocker.

### Minimal correction

Use the same audited absolute executable path for the version probe as for supervisor launch, with descriptor/path identity checks immediately before and after the version subprocess.

Minimal shape:

1. retain the already-open, hashed `executable_fd`;
2. verify `lstat(executable)` identity equals the retained descriptor identity;
3. invoke `[str(executable), "--version"]`;
4. re-check the pathname identity against the retained FD immediately after;
5. re-hash/re-check the retained FD as already done;
6. supervisor then repeats its before/after path identity checks for `serve`.

Do not weaken unknown-listener rejection or the retained-descriptor digest checks.

Add a platform-aware regression that proves the version probe uses the audited path rather than `/dev/fd` on Darwin.

### macOS same-user replace-and-restore race

The path-based launch/version probe necessarily leaves a short same-user pathname TOCTOU window because Darwin cannot atomically exec the retained descriptor with the approved standard-library/no-helper scope.

**QA determination: acceptable residual within the currently approved local threat model, but only as a documented residual.**

Reason:
- the project has already explicitly defined the local POSIX protections as **not defense against an arbitrary compromised same-user host** (Task 7A Correction 03);
- parent directories are required to be root/current-user owned and not group/other writable;
- executable file is no-follow, single-link, current-user owned, hashed through a retained FD and identity-checked around use;
- no external/untrusted caller may supply the executable path/runtime lock.

A hostile process already running as the same user can deliberately replace-and-restore an owner-writable executable between checks. That is a real race, not eliminated by this code. It is acceptable only because arbitrary compromised same-user host behavior is outside the established local threat model. It must remain a Gate-B residual risk and cannot be described as atomic executable identity enforcement.

A future stronger threat model would require a native FD-exec/helper, sandboxed service architecture, immutable/root-owned executable deployment, or another separately approved OS mechanism.

## Finding 2 — LOW / correctness — failed supervisor Popen can raise UnboundLocalError instead of sending ERROR handshake

### Exact source

In `_supervisor_main()`, `child` is assigned only by:

`child = subprocess.Popen(...)`

but the surrounding `except OSError` immediately evaluates:

`if child is not None:`

If `subprocess.Popen` itself raises `OSError`, `child` has never been assigned.

### Independent reproduction actually run

Code-only Python reproduction of the exact local-variable structure with an invalid executable produced:

`UnboundLocalError: cannot access local variable 'child' where it is not associated with a value`

This does **not** orphan a child in that branch, because no child was successfully created and OS process exit closes the supervisor descriptors. The parent launcher still observes missing/invalid handshake and fails closed, so this is not a separate high-severity security issue.

### Minimal correction

Initialize before the try:

`child: subprocess.Popen[bytes] | None = None`

Then retain the existing cleanup/ERROR-handshake path.

Add an assertion that a true Popen failure returns the intended `ERROR\n` supervisor status rather than merely relying on supervisor process death.
