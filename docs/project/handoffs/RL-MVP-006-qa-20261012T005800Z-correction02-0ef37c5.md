## NEW BLOCKING finding — canonical summary-member ordinal tamper is not detected on reopen

Severity: **Medium / authoritative persistence-integrity acceptance failure**.

The Correction-02 packet explicitly requires reopen/tamper checks including **member-order/ordinal verification**.

Authoritative summary persistence writes `summary_members` in canonical order:

- `snapshot.requested_attempt_ids` is sorted;
- rows are inserted using `enumerate(snapshot.requested_attempt_ids)`.

However `EvaluationStore.get_summary` only verifies that:
- rows sort by ordinal;
- each returned ordinal is contiguous `0..N-1`.

It does **not** verify that:

`member_row["subject_id"] == stored.requested_attempt_ids[ordinal]`

or otherwise bind each persisted ordinal to the canonical ordered membership in the stored snapshot.

The rebuilt v3 snapshot again sorts requested attempt IDs, so a permutation of whole member rows across ordinals is normalized away.

### Reproduction

For stored canonical membership:

`("attempt-a", "attempt-b")`

tamper member rows to:

- ordinal 0 -> `attempt-b`
- ordinal 1 -> `attempt-a`

The current ordinal-contiguity check passes:

`[0, 1]`

The reconstructed requested attempt tuple is sorted back to:

`("attempt-a", "attempt-b")`

and therefore matches the stored snapshot identity.

Independent isolated result:

- ordinal check: **PASS**
- rebuilt canonical membership equals stored canonical membership: **True**
- order/ordinal tamper: **not detected**

For included members, swapping the complete subject/evaluation pair across ordinals likewise preserves each evaluation-to-attempt binding and the same exact membership set. For exclusion-only summaries there is no evaluation binding at all, making the gap especially direct.

### Why this is blocking

The packet did not merely require set-equivalent replay; it explicitly required member-order/ordinal tamper verification for the authoritative repository.

The current implementation persists an ordinal as authoritative row state but does not verify its canonical subject association on reopen.

Normal immutability triggers prevent routine mutation, but the packet's tamper/reopen tests deliberately require defense-in-depth verification after immutable-store protection is bypassed or corrupted.

### Required correction

On reopen, validate canonical ordinal membership before rebuilding, for example:

- require the ordered `summary_members.subject_id` sequence to equal `stored.requested_attempt_ids`; and
- where applicable require stored disposition/evaluation/exclusion bindings to correspond exactly to the canonical member at that ordinal.

Add adversarial tests that drop the member immutability trigger, swap two whole member rows' ordinals, and verify `get_summary` rejects the stored evidence rather than normalizing the permutation away.

No schema migration is necessary.
