## BLOCKING finding — no interprocess startup coordination; cleanup can delete another live helper's backup

Severity: **Medium-High / backup availability and deterministic-startup integrity**.

The parent uses a module-local `threading.RLock`, which protects only concurrent initializers inside the **same Python process**.

There is no cross-process startup lock or equivalent ownership mechanism.

This creates two independent races when two application processes start against the same database:

1. **Migration-version race.** Both helpers may read the same pre-migration schema state. One commits version 1; the second subsequently attempts the same immutable migration insert and fails with a uniqueness error.

2. **Active backup cleanup race.** `_cleanup_incomplete_backups` deletes every matching current-user `.bak.part` at helper startup. It has no age, owner-token, lock or liveness check. A second startup can therefore unlink the first helper's actively written temporary backup. The first helper's open FD remains valid, but final publication by temporary filename fails.

The authoritative database remained recoverable in my isolated probes, so I did **not** observe Task-4/6 evidence corruption. This is nevertheless a blocking acceptance gap because the packet requires deterministic restart/backup cleanup and the user explicitly asked for simultaneous independent process startup to be challenged.

An active backup is not the same thing as an abandoned incomplete backup, yet the current cleanup treats both identically.

### Required correction

Add interprocess migration/startup coordination or a backup ownership/liveness protocol that prevents one helper from cleaning another active helper's `.part`.

Then ensure a second independent application process either:
- waits and re-reads the committed migration checksum cleanly; or
- fails before touching another process's live backup, with a deliberate single-instance error that cannot disturb the winning initializer.

Add a real two-process regression covering:
- simultaneous launch on a legacy database;
- no active `.part` deletion;
- exactly one migration application;
- the loser/waiter reopens deterministically;
- Task-4/6 rows remain byte-equivalent.
