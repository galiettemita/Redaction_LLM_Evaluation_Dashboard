## BLOCKING finding 1 — parent/root symlinks can escape the application artifact root

Severity: **High / filesystem confinement defect**.

E0044 explicitly requires defense against symlink traversal and storage outside the checkout/web root at controlled platform paths.

The implementation checks only the final artifact path with `candidate.is_symlink()` and uses `O_NOFOLLOW` only on the final file read.

It does **not** prevent symlink traversal through:
- `REDACTION_LAB_HOME` itself;
- `artifacts` / `temporary` roots when constructed directly;
- content-addressed parent directories such as `artifacts/sha256/<prefix>`.

`resolve_paths` calls:

`root = root.resolve(strict=False)`

before `initialize_paths` performs its symlink check. An existing symlink is therefore silently resolved to its target; the later `root.is_symlink()` check cannot detect the original symlink.

Likewise, `ArtifactStore.publish` calls `destination.parent.mkdir(..., exist_ok=True)` and then `os.replace(..., destination)`. If the hash-prefix directory is a symlink to another directory, publication follows that parent symlink and writes outside `artifact_root`.

This is a concrete path escape, not merely malformed logical-key input.

### Required correction

Use an explicit no-symlink path policy across the entire configured root and artifact parent chain before writes/reads, not only the leaf path.

At minimum:
- reject an explicit application home if any existing component is a symlink rather than canonicalizing it away;
- reject symlinked artifact/temporary roots;
- reject symlinked `sha256` and digest-prefix parent directories;
- perform directory-relative operations using trusted directory file descriptors / `O_NOFOLLOW`-style primitives where available, or equivalent fail-closed checks that avoid the current check-then-use gap;
- add adversarial regressions for root symlink, prefix-directory symlink and replacement races as feasible in the supported platform scope.

## BLOCKING finding 2 — a mocked/custom worker can mint Task-4 authority without an enforceable qualified-runtime binding

Severity: **High / authoritative PDF-derived evidence boundary**.

The E0045/E0046 design requires worker observations to remain untrusted and host authority to be bound to verified isolation/runtime provenance.

The production-facing `DocumentWorker` constructor accepts any object implementing the `PdfWorker` protocol:

`DocumentWorker(store, artifacts, isolated_worker: PdfWorker)`

The code does not require this dependency to be an `IsolatedPdfWorker`, nor does it independently compare `VerifiedWorkerResult.image_digest` against an application-owned approved RuntimePolicy before constructing a Task-4 source.

The test suite demonstrates the seam directly with `SyntheticWorker`: its mocked `VerifiedWorkerResult` is sufficient for `DocumentWorker` to persist an authoritative Task-4 canonical source.

The subsequent Task-4 bridge validates:
- actual PDF SHA;
- project;
- approved detector/canonicalizer version strings;
- bounded geometry/order;
- deterministic IDs;
- marker/canonical hash consistency.

It **cannot** verify that canonical text or geometry was actually derived from those PDF bytes.

Because `RunStore` also accepts a composition-injected `source_deriver`, a custom derivation callback can return structurally valid worker-derived material and obtain Task-4 persistence without any RunStore-level runtime/protocol/image capability.

This is exactly the adversarial case requested for review: a mocked worker response can assert authoritative PDF-derived evidence.

### Why this is different from the accepted semantic limitation

It is acceptable that a *qualified isolated parser* remains the semantic trust root and that the host cannot cryptographically re-prove parser semantics without reparsing.

The defect is that the authoritative persistence path does not enforce that the material came from that qualified parser/runtime at all; it relies on trusted Python object composition.

No public API exists yet, so an external upload caller cannot currently inject the object directly. However E0046 specifically introduces the worker trust interface, and this seam is the point at which Task-4 authority is minted.

### Required correction

Introduce an enforceable production authority boundary, for example:
- a non-forgeable/internal capability produced only by successful `IsolatedPdfWorker` runtime verification and consumed by the Task-4 source bridge; or
- a single application-owned derivation service that owns the RuntimePolicy and does not accept arbitrary PdfWorker/source-deriver substitution in the authoritative path; or
- equivalent binding that verifies approved runtime/image/protocol provenance at the same point Task-4 source authority is created.

Keep test mocks behind a test-only/non-authoritative seam.

Add a regression proving that a caller-created/mock `VerifiedWorkerResult` or arbitrary injected source-deriver cannot create an authoritative Task-4 source.
