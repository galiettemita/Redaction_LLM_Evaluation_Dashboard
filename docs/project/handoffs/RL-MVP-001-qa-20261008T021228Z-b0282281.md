## Observed defects

### STOP / Critical — PredictionManifest can carry and serialize reference-derived content

`PredictionManifest.settings` is `dict[str, Any]`. The candidate rejects a top-level extra field named `reference_text`, but accepts it inside the allowed settings field. Reproduction:

`PredictionManifest(..., settings={"nested": {"reference_text": "LEAK"}})`

constructs successfully, and `model_dump(mode="json")` serializes the secret. This violates the prediction/reference isolation requirement that reference/evaluator fields be structurally unavailable to prediction workers. Top-level `extra="forbid"` does not protect nested free-form settings.

This is a review stop condition because the contract itself permits reference leakage into the predictor-facing payload.

### High — Records described as immutable are only shallowly frozen

Pydantic `frozen=True` prevents attribute reassignment but does not freeze nested mutable objects. Independent mutations succeeded after construction and changed subsequent serialization for:
- `RedactionTarget.detection_evidence`
- `RunDefinition.settings`
- `PredictionManifest.settings`
- `ModelAttempt.usage`
- dictionaries inside `EvaluationRecord.fact_comparisons`

Example: mutating `target.detection_evidence["nested"]["x"]` after creation changes `model_dump()`. This breaks the stated frozen/immutable record boundary and can invalidate hashes, provenance and replay assumptions.

### STOP / Critical — CONFIRMED truth can be constructed without required reference/alignment evidence

A `ReferenceMapping(status=CONFIRMED, exact_revealed_text="secret")` is accepted with:
- `reference_document_version_id=None`
- no token locator
- no redacted/reference canonical hashes
- no global alignment version
- empty left/right anchor evidence

The validator checks only that confirmed mappings have nonblank text. The approved contract says confirmed truth requires complete, unique, readable, reliably aligned evidence. The current record can therefore claim confirmed truth without the fields needed to establish or audit those conditions.

Minimum safe ownership boundary: contract-level validators should enforce all locally checkable coherence (reference identity, required evidence/version fields and explicit scoreability evidence). Cross-record existence and provenance checks that require reading stored records should be enforced transactionally by the reference/evaluation service before allowing a scoreable mapping downstream.

### STOP / Critical — VERIFIED EvaluationRecord can be created without any mapping identity

The following is accepted:

`EvaluationRecord(status=VERIFIED, mapping_id=None, mapping_version=None, verified_score=1.0, ...)`

The score-channel validator only separates verified vs experimental numeric fields. It does not require a reference mapping for VERIFIED status or bind the evaluation to a scoreable mapping. This creates a direct contract path to a false verified score.

At minimum, VERIFIED must require mapping identity/version at the record layer; the evaluation service/store must additionally verify that the referenced mapping exists, matches the attempt target/version, and is CONFIRMED/scoreable under the current mapping policy before persistence.

### STOP / Critical — SummarySnapshot permits a verified score with zero eligible denominator

`SummarySnapshot(eligible_count=0, verified_score=1.0, included_evaluation_ids=(), ...)` constructs successfully. This conflicts with DEC-004/DEC-014 and the explicit zero-denominator rule: no eligible verified items means no verified score, not 0 or any positive percentage.

### High — Summary contract does not identify the required aggregation scope

`SummarySnapshot` contains `model_id` and `condition_id` but no document/document-version identifier or explicit summary level/scope. From the record alone, a consumer cannot distinguish a per-document model summary from a cross-document per-model summary. This is insufficient to safely represent all three required reporting levels without an external convention.

### Medium — Core identifiers and target marker accept empty strings

A `PredictionManifest` with empty manifest/run/target/version/model/prompt IDs and an empty target marker constructs successfully. Similar identifier fields are unconstrained plain strings across the contracts. This creates collision/serialization risk for later persistence and worker idempotency. Non-empty constraints or dedicated ID types should be established before downstream consumers rely on these records.
