## BLOCKING finding 1 — required model-level cross-document summaries are incompatible with the existing run contract

Severity: **Critical functional/contract defect**.

`summary._validate_common` requires all evaluations in a summary to have the same `run_id`.

That is valid for a per-document summary, but it makes the required **per-model-across-document** summary incompatible with Task 4's frozen run semantics:

- `RunDefinition` identifies one `canonical_document_version_id` and one canonical hash.
- Task-4 `build_prediction_manifest` requires that run to match exactly that canonical document.
- Task 4 also requires exactly one selected model per run.

Therefore legitimate evaluations from:
- two different documents, or
- two different model-specific runs

normally have different run IDs.

Independent probe:
- document 1 evaluation: `run-doc-1`
- document 2 evaluation: `run-doc-2`
- same model/config/condition/rubric/judge
- `_validate_common` result: **REJECTED — incompatible run_id**

The shipped test `test_model_summary_spans_documents_but_never_models` passes only by assigning the **same run ID to two different redacted document versions**, which does not represent a legitimate Task-4 run binding.

The same problem appears in `assert_comparable_summaries`: it requires model summaries to share the same `run_id`. Because Task 4 uses one selected model per run, two legitimate model summaries for different requested models cannot share a truthful immutable RunDefinition identity.

This means the implementation cannot produce the required third score/reporting level over real valid upstream records without either:
- reusing a run ID across different immutable runs/documents/models, or
- rejecting the aggregation.

**Required correction:** separate *run-local provenance* from *cross-run comparability provenance*. Model summaries should be able to combine distinct run IDs only when the required compatible prompt/settings/condition/model/rubric/reference provenance is explicitly represented and verified. Cross-model comparison likewise cannot use same-run identity as a proxy when upstream run semantics permit one selected model.

## BLOCKING finding 2 — directly constructed forged EvaluationRecords are accepted as software-trusted synthetic evidence and summaries trust them

Severity: **Critical trust-boundary defect**.

The Task-6 contract validator is structural, not authoritative. A caller can directly construct an immutable `EvaluationRecord` with:
- arbitrary project/run/target IDs;
- arbitrary mapping/source-fact IDs;
- `reference_trust="APPROVED_SYNTHETIC_PAIR"`;
- `mapping_status=CONFIRMED`;
- `mapping_scoreability=SCOREABLE`;
- arbitrary reference/canonical version strings;
- arbitrary typed `FactComparison` evidence;
- null numeric score channels.

Independent probe: such a forged record **successfully validates**.

`summary._is_truth_eligible` then trusts only these record fields:

`reference_trust == APPROVED_SYNTHETIC_PAIR && mapping_status == CONFIRMED && mapping_scoreability == SCOREABLE`

The forged direct record is therefore treated as eligible without re-resolving DEC-022 PDF bytes, mapping authority, source-fact authority, attempt authority or deterministic evaluation identity.

This defeats the evaluator's stronger trust checks if the summary layer receives caller-created `EvaluationRecord` objects instead of only records produced by `evaluate_attempt`.

The Backend handoff acknowledges there is no authenticated evaluation-record repository yet, but the Task-6 summary API itself has no trust token/resolver or deterministic-record verification. The user's requested direct-construction probe therefore exposes a concrete bypass, not merely missing persistence.

**Required correction:** summaries must consume records whose evaluator provenance can be independently verified, or revalidate a deterministic evaluation identity/evidence envelope sufficient to prevent caller-created records from claiming `APPROVED_SYNTHETIC_PAIR`. If that authority requires a separate durable trusted repository/contract, stop and request the needed scope rather than assuming all `EvaluationRecord` instances are trusted.

## BLOCKING finding 3 — directly constructed forged SummarySnapshots can claim internally consistent evidence without any source EvaluationRecords

Severity: **High provenance-integrity defect**.

The Task-6 `SummarySnapshot` validator correctly checks structural reconciliation, but it does not bind:
- included evaluation IDs to actual EvaluationRecords;
- eligible target keys to those records;
- model/condition/rubric/version sets to the included records;
- `summary_id` to a recomputed summary payload.

Independent probe: a completely synthetic `SummarySnapshot` with:
- `included_evaluation_ids=("forged-eval",)`
- `eligible_evaluation_ids=("forged-eval",)`
- a self-consistent fake target key
- a correctly recomputed common-set ID
- fake project/model/run/rubric/judge/reference version values
- all counts internally reconciled
- null numeric scores

**constructs successfully**.

Immutability after construction does not establish provenance before construction.

This is directly relevant to the requested “direct construction of forged evaluation or summary records” check. If summaries are externally consumed as evidence records, a structurally valid object is not proof it came from `summarize_*()`.

**Required correction:** add a deterministic summary identity/integrity verification path tied to the exact included evaluation records, or make the trusted application repository/builder boundary explicit and enforceable before these records can be treated as authoritative summaries.

## BLOCKING finding 4 — evaluator does not establish that the supplied ModelAttempt is an authentic frozen Task-4 attempt

Severity: **High prediction-provenance defect**.

`evaluate_attempt` validates:
- project;
- target ID/version;
- reference/canonical target binding.

It does **not** verify the supplied `ModelAttempt` against:
- a trusted `PredictionManifest`;
- a trusted `RunDefinition`;
- Task-4 `RunStore` durable attempt provenance;
- prompt ID/version;
- settings;
- attempt policy;
- canonical input hash used for the attempt.

A caller-created `ModelAttempt` with the correct project/target/version but arbitrary:
- prediction text,
- attempt ID,
- run ID,
- model/model-config ID,
- request/response hashes

can therefore be semantically evaluated against trusted reference truth.

This violates the Task-6 objective of evaluating a **frozen prediction attempt** and undermines the requested “frozen predictions versus reference/evaluator content” separation. Immutability of a forged Pydantic object is not evidence that the attempt originated from the durable prediction worker.

**Required correction:** bind the evaluator to trusted Task-4 attempt/manifests/run provenance, or require a trusted resolver/store verification before semantic evidence can be created.

## Research-facing limitation — source-fact propositions and mock labels remain supplied, not independently verified

The implementation does correctly enforce exact quote membership and quote locator integrity. It does **not** establish that a supplied `reference_proposition` is semantically entailed by the exact quote, nor that the supplied source-fact set is complete.

Independent source-level probe confirms that a fabricated proposition can satisfy the current mechanical checks as long as its quote and locator are valid.

A single caller-supplied fact labeled SUPPORTED can then produce:
`PROVISIONAL_ALL_FACTS_SUPPORTED`

This is explicitly marked provisional and no numeric score is created, so I do not treat this alone as a software blocker beyond the trust-chain defects above. It is nevertheless a material scientific limitation and must not be displayed as independently verified semantic accuracy. The designated Research review must assess whether the current COMPLETE / PROVISIONAL labels sufficiently preserve the Task-5 “proposal only / not human gold” boundary.

## Other observations / nonblocking concerns

- Summary builders always emit `excluded_count=0` and no excluded IDs. There is no builder API for requested-but-excluded targets, despite the Task-6 summary contract asking for exclusions. This should be reconciled before UI/report consumers depend on exclusion counts.
- `condition_id` is caller-provided to `evaluate_attempt`; it is not independently bound to a trusted RunDefinition experiment condition.
- Evaluation records do not carry prompt ID/version/settings/attempt-policy provenance, yet the Task-6 packet requires incompatible prompt/settings conditions not be pooled. The current same-`run_id` rule masks this gap by over-constraining valid cross-run aggregation rather than representing the required provenance directly.
- Truth eligibility is intentionally orthogonal to attempt outcome: a TIMEOUT can have trusted truth and be in the eligible truth set while also counted as timeout. This is not double-counting because the summary contract treats truth partition and attempt-outcome partition as separate dimensions.
- Empty eligible sets remain numeric-null as required.
