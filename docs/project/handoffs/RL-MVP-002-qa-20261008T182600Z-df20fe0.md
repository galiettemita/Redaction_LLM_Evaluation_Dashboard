## Three previously blocking issues

### 1. Staggered sparse columns — RESOLVED

The v5 layout helper no longer relies on the prior 48 pt vertical cutoff. Independent probes at 40, 49, 52, 60, 80 and 140 pt separation all returned ambiguous/unsupported for disjoint column-separated one-line spans.

Same-line two-column and sparse one-line secondary-column variants also remain rejected. Ordinary single-line and modestly indented single-column controls were not falsely classified.

### 2. Short / offset no-glyph redaction boxes — RESOLVED for the routed cases

The candidate now treats no-glyph rectangles with text-line-like height (one-half to two times median visible glyph height) as plausible text rectangles regardless of width or page position. This closes the prior 18–20 pt width and x=260/280/300 false-NO_REDACTIONS escapes for the 14 pt-high routed boxes.

The remote text-sized decorative case is conservatively UNSUPPORTED rather than silently ignored, matching the documented supported-layout boundary.

### 3. Short centered heading false positive — RESOLVED for the approved heading envelope

The v5 exception accepts a centered larger heading only when at least two remaining single-span body lines establish aligned single-column flow. Independent probes confirmed:
- short centered heading + two aligned body lines -> not ambiguous;
- same heading + only one body line -> UNSUPPORTED;
- modest single-column indentation remains allowed.

This matches the Correction 04 supported-layout boundary.

## New blocking regression: remote square/wide artwork aligned with the text x-range is treated as ambiguous

The review packet explicitly requires checking **remote square/wide artwork** separately from remote text-sized decorative rectangles.

The candidate's `_plausible_text_rectangle` begins by returning true whenever the rectangle's horizontal x-range overlaps any visible character x-range, **without considering vertical distance or rectangle height**. Only when there is no x-overlap does it use the declared text-line-height envelope.

As a result, clearly remote non-text artwork can be forced into `AMBIGUOUS_TEXT_FLOW_RECTANGLE` merely because it shares the same horizontal column as text. Independent probes using the exact predicate show:
- remote 40x40 square at the same x-range as body text -> plausible **True**
- remote 120x30 wide/tall rectangle at the same x-range -> plausible **True**
- the same shapes moved off the text x-range -> plausible **False**

For a no-glyph rectangle these true results enter the candidate's fail-closed unsupported path rather than the remote-artwork ignore path. This contradicts the Backend handoff's stated rule that geometry outside the text-line-height class may be ignored when it lacks actual character overlap and same-line-flow evidence, and it regresses the routed remote square/wide artwork negative control by making x-overlap alone sufficient evidence.

This is not a leakage or false-target defect—the candidate fails closed—but it is a supported-input classification regression in the explicit Correction 04 review matrix. A simple single-column page with a decorative black square far below the text but vertically unrelated can be rejected solely because it sits under the same x-range.

Required correction: distinguish **2D character/text-flow evidence** from horizontal alignment alone. For geometry clearly outside the text-line-height class and vertically remote from visible text, preserve remote-artwork exclusion even when x-ranges overlap. Keep text-height remote rectangles conservative/UNSUPPORTED as documented.
