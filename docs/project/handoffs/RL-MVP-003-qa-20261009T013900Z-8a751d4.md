## BLOCKING finding — canonical-version provenance is still caller-forgeable

Severity: **High / provenance-integrity blocker**.

DEC-022 requires binding the redacted canonical project/version to the approved pair and mappings require versioned provenance. The public gate currently pins:
- project ID,
- redacted document-version ID,
- reference document-version ID,
- actual redacted bytes,
- actual reference bytes.

It does **not** pin or independently derive the canonical-version identities that are later persisted into confirmed mappings.

### Redacted canonical version

`_redacted_records_match_pdf` rebuilds the canonical record using:

`canonical_document_version_id=redacted.canonical_document_version_id`

That value comes from the caller-supplied `CanonicalRedactedDocument`.

Therefore, if an attacker/caller takes the genuine pinned redacted PDF and otherwise genuine canonical content/hash/targets, but changes only `canonical_document_version_id` to an arbitrary forged nonblank value, the rebuild is performed using that same forged value. The rebuilt object can equal the forged caller object, so the check is self-fulfilling rather than independently authoritative.

The existing forged-canonical regression changes `canonicalizer_version`, which is independently regenerated and therefore correctly fails. It does not cover a forged `canonical_document_version_id`.

### Reference canonical version

The public API accepts any nonblank `reference_canonical_version_id`. The registry does not pin it. The reference canonicalizer is then invoked using that caller-supplied ID, and a CONFIRMED mapping records it as `reference_canonical_version_id`.

Thus a byte-identical approved pair can still yield a CONFIRMED mapping that asserts arbitrary canonical-version provenance.

### Why this matters

This does not alter the pinned synthetic truth text, so it is not a content-level false-CONFIRMED finding. It is a version-integrity defect in the exact evidence record. The project requires mappings/evaluations to carry trustworthy versioned provenance, and the DEC-022 packet explicitly requires binding the redacted canonical project/version to the trusted pair rather than accepting caller-created identity as authority.

A mapping should not be SCOREABLE/CONFIRMED while carrying canonical-version IDs that were never independently pinned or derived.

### Required correction

For the approved synthetic pair, either:
1. pin the expected redacted and reference canonical-version IDs in the application-owned registry and validate them before CONFIRMED, or
2. derive fixed application-owned canonical IDs internally for the registered pair rather than accepting caller-selected canonical IDs.

Add regressions for:
- correct pinned bytes + forged redacted `canonical_document_version_id`;
- correct pinned bytes + forged `reference_canonical_version_id`;
- confirmed mapping provenance exactly matching the approved canonical identities.

Both forged cases should return NOT_SCOREABLE/null (or reject input) rather than CONFIRMED.
